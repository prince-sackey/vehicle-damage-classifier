# Vehicle Damage Classification for Insurance Claims

A 6-class image classifier that identifies vehicle damage type — crack, dent, glass shatter,
lamp broken, scratch, or tire flat — the kind of triage step an insurer could use to route or
pre-assess a claim from a submitted photo.

Two models are trained and compared:
- **Baseline CNN** — a small convolutional network trained from scratch.
- **MobileNetV2 (transfer learning)** — an ImageNet-pretrained backbone with a new classification head.

## Results

MobileNetV2 reached **84.2% accuracy** on a held-out test set of 1,088 images, ahead of the baseline
CNN's ~74% validation accuracy. This held up across a clean, full rerun of the notebook (84.2% vs.
84.0% on the first run), confirming the result is stable rather than a one-off.

| Class | Precision | Recall | F1 | Support |
|---|---|---|---|---|
| Glass shatter | 0.98 | 0.94 | 0.96 | 190 |
| Tire flat | 0.95 | 0.93 | 0.94 | 85 |
| Scratch | 0.82 | 0.82 | 0.82 | 335 |
| Dent | 0.76 | 0.86 | 0.81 | 310 |
| Lamp broken | 0.85 | 0.72 | 0.78 | 145 |
| Crack | 0.83 | 0.43 | 0.57 | 23 |

Glass shatter and tire flat are classified almost perfectly. Crack is the weak spot (recall 0.43),
most likely due to having far fewer training examples (23 in test vs. 300+ for dent/scratch) rather
than being inherently harder to detect — more labeled crack images would likely close most of this
gap. See the notebook's confusion matrix for exactly which classes get mixed up.

## Debugging the deployment: a double-preprocessing bug

Test-set accuracy said 84%, but early testing on real-world photos (a night-time crash scene, a
rain-soaked taillight, a fresh dent) told a very different story: every single image, regardless of
what damage it actually showed, came back as "scratch" with 90%+ confidence.

The tell wasn't that the predictions were wrong — it was that they were wrong in the *same way*
every time. A model that's genuinely struggling with unfamiliar photos produces varied, uncertain
guesses. A model producing the identical confident answer across completely different images
usually means the input itself is broken before it ever reaches the model's learned features.

The cause: the model's own architecture already applies `mobilenet_v2.preprocess_input()` as its
first layer —

```python
inputs = Input(shape=(224, 224, 3))
x = tl_augmentation(inputs)
x = preprocess_input(x)      # baked into the model
x = base_model(x, training=False)
```

— but the deployment app called `preprocess_input()` a second time, manually, before passing the
image to `model.predict()`. MobileNetV2's preprocessing rescales pixels to roughly [-1, 1]; running
it twice pushes every image into the same distorted range, regardless of what the photo actually
shows. That's exactly the "consistent wrong answer" signature.

**Fix**: removed the redundant manual preprocessing call from `app.py` and `streamlit_app.py` — the
model already handles it internally. No retraining needed.

**Before and after**, same photos:

| Photo | Before (buggy) | After (fixed) |
|---|---|---|
| Night-time crash scene, full car in frame | scratch (high confidence) | dent 87.3%, glass shatter 9.1% |
| Rain-soaked taillight, close-up | scratch 91.2% | lamp broken 41.1%, dent 31.9%, scratch 26.8% |
| Fresh dent/tear, close-up | scratch 95.0% | dent 99.2% |

The 84% test accuracy was real all along — the deployed app was just showing a broken input
pipeline, not the model's actual behavior.

## Repo contents

| File | Purpose |
|---|---|
| `vehicle_damage_classification.ipynb` | Full training notebook — data pipeline, both models, test-set evaluation, confusion matrix |
| `app.py` | Gradio app that loads the saved model and classifies an uploaded photo (deployed on Hugging Face Spaces) |
| `streamlit_app.py` | Streamlit app doing the same thing (deployed on Streamlit Community Cloud) |
| `requirements.txt` | Dependencies for both deployment apps |
| `vehicle_damage_mobilenetv2.keras` | Saved trained model (generated by the notebook) |
| `class_names.json` | Class index → label mapping (generated by the notebook) |

## Running the app locally

```bash
pip install -r requirements.txt
python app.py
# or
streamlit run streamlit_app.py
```
